# Ревью агентов claude-dev-agents на фоне трёх внешних источников

Дата: 2026-10-29. Репозиторий: v1.21.0 (16 агентов, 6 скиллов).
Статус на 2026-10-30: все 12 пунктов плана реализованы в релизах v1.22.0 по v1.32.1 (18 агентов,
12 скиллов); по ходу работы analyst-writer оставлен тонким агентом для веера, а не переведён в скилл
целиком, js-developer добавлен, в sql-patterns вошли SQLite и NoSQL. Текст ниже сохранён как исходный
разбор без правок задним числом.
Источники: статья Anthropic «When to fold subagents into your main agent loop»,
[openronin/openronin](https://github.com/openronin/openronin) (автономный dev-бот на GitHub, альфа, 11 звёзд),
[Donchitos/Claude-Code-Game-Studios](https://github.com/Donchitos/Claude-Code-Game-Studios) (49 агентов, 74 скилла, 28,5 тыс. звёзд).

## Вердикт в двух абзацах

Декомпозиция по зонам в целом верная, но по разным причинам для разных групп. Ревьюеры (7 агентов)
оправданы как сабагенты по всем трём критериям статьи: им нужен холодный контекст, они читают много и
возвращают компактный результат. Генераторы документов (architect, backlog-planner, qa-expert, data-analyst)
оправданы по критерию «много чтения, короткий выход». Слабое звено это билдеры (php-developer,
python-developer) и два «разговорных» агента (analyst-writer, facilitator): при вызове как сабагент они
теряют контекст беседы, а задать вопрос пользователю посреди работы не могут. Переводить всё на скиллы не
нужно. Facilitator переводится в скилл; у analyst-writer знание уезжает в скилл, а тонкий агент остаётся
для веера (N аналитиков пишут N описаний задач) и пакетной работы; билдерам нужен контракт входа.

Универсального пайплайна нет ни у одного из источников, и это не случайно. Зато у обоих репозиториев
есть одна и та же конструкция: фиксированный скелет стадий плюс конфиг на уровне проекта, который
включает и выключает стадии. У openronin это список `lanes:` в YAML репозитория, у Game Studios это
`modes.rigor` в `project.yaml`. Для claude-dev-agents нужен именно такой скелет и скилл (не агент),
который на старте проекта заполняет конфиг в диалоге с пользователем и пишет его в репозиторий.

## Что говорят источники

### Статья Anthropic: сабагент должен быть оправдан, а не задан по умолчанию

Тезис: в нескольких корпоративных внедрениях один агент со скиллами и прогрессивным раскрытием
инструментов обгонял оркестратор с сабагентами по качеству, цене и задержке. Цена сабагентов это потеря
деталей на передаче (сабагент возвращает резюме, главный агент сырых результатов не видит), «испорченный
телефон» при делении по типу задачи, расползание пересекающихся сабагентов без владельца и вложенные
циклы (один клиент получил двукратное ускорение, свернув оркестратор).

Три условия, при которых сабагент остаётся:
- один цикл измеримо деградирует от раздувания контекста;
- задачи параллельны и каждой нужен свежий контекст, который после задачи можно выбросить;
- один агент путается в выборе инструментов или в системном промпте конфликтуют инструкции.

Правило деления: «по контексту, а не по типу проблемы». Хороший сабагент получает работу, которой
мало что нужно от остальной системы, и возвращает компактный результат: независимый поиск, компонент
с чистым интерфейсом, проверка чёрного ящика. Передавать беседу целиком только когда сабагент должен
говорить с пользователем. Сильно связанных специалистов (которые работают по выходу друг друга, трогают
одни данные, вызываются вместе) сливать первыми. Менять по одному, сравнивать на eval.

Ограничение статьи. Она про агентов на API, где сабагент это вложенный цикл в коде заказчика. У сабагентов
Claude Code есть свойства, которых статья не оценивает: своя модель на агента (sonnet для билдеров),
ограничение инструментов в frontmatter (ревьюер физически не может писать), параллельный веер из
главного цикла. Критерии статьи применимы, цифры нет.

### openronin: детерминированный роутер и три слоя по стоимости

Задача идёт по «lanes» (полосам): triage, analyze, patch, pr_dialog, conflict_resolve, auto_merge,
deploy. Полоса это тройка «триггер, движок, выход». Роутер это одна функция `pickLane`, автор прямо
пишет «никакого непрозрачного агентского цикла, решающего, что дальше». Три слоя разделены по роли и
цене: Director (источник намерений, никогда не правит код), Supervisor (дешёвая модель, читает,
классифицирует, задаёт вопросы), Coder (единственный, кому разрешено менять код, и только в изолированном
worktree). По графику автора supervisor обрабатывает 80% ходов за 10% расходов.

Что переносится в наш проект:
- **Контракт выхода в строгом JSON** на каждую полосу: analyze возвращает `state: ready | needs_clarification`,
  `expanded_requirements`, `questions[]`, `files_likely_touched`. Билдер получает на вход не тикет, а
  расширенные требования от аналитика.
- **Терминальные состояния с ярлыками**: `awaiting-answer`, `awaiting-action`, `needs_human`,
  `guardrail_blocked`. Тупик всегда виден, молчаливых отказов нет.
- **Ограничители**: `max_diff_lines`, `protected_paths`, потолок итераций диалога по PR (10), потолок
  попыток разрешения конфликтов (3).
- **Чартер репозитория** для Director: видение, приоритеты с весами, зоны «не трогать», definition of
  done. Чартер версионируется, каждое решение привязано к версии. Это и есть «пайплайн, записанный на
  уровне проекта».
- **Лестница доверия**: `dry_run`, `propose`, `semi_auto`, `full_auto`. Несколько дней в dry_run для
  калибровки чартера, потом подъём.
- **Внимание на застрявшее раньше нового**: watchdog подаёт список stale PR и зависших вопросов, и
  Director обязан разобрать их до планирования. Пустой тик это допустимый результат.
- **Standing notes**: фраза оператора, похожая на устойчивое предпочтение, сохраняется решением
  `remember_preference`, а не тает в окне чата.

Минусы для нас. Всё это код на TypeScript, а не промпты: роутер, ограничители и состояния живут в
`src/scheduler/worker.ts`, перенести «как есть» в Claude Code нельзя. Ревьюер в режиме patch_multi это
32 строки промпта с JSON-ответом, наши ревьюеры глубже на порядок. Один кодер на все языки. Проект в
альфе на 11 звёздах; переносятся концепты, а не реализация.

### Game Studios: пайплайн живёт в скиллах, агенты это роли

Три яруса агентов (директора, лиды, специалисты) и правила координации: вертикальная делегация,
эскалация к общему родителю, запрет на правки вне своей директории. Но рабочие цепочки записаны не в
агентах, а в скиллах: `/dev-story` загружает историю, ADR, манифест, роутит к нужному программисту и
оставляет историю готовой для `/story-done`; `/team-combat` гонит шесть агентов через фазы с точкой
решения на каждом переходе.

Что переносится:
- **CONTRACT.md у скилла**: «Role in pipeline», «Inputs required» (какие файлы и секции должны
  существовать, что read-only), «Outputs produced» с гарантиями, «Immutability rules», «Downstream skill
  expects», «Known fragile points». Это самая конкретная форма контракта между звеньями из трёх источников.
- **Один рычаг `modes.rigor`** (minimal, standard, full), от которого разворачиваются `workflow` (какие
  документы обязаны существовать до кода), `automation` (collaborative, guided, autonomous: когда
  спрашивать), `review_mode` (глубина гейтов) и `team.size` (сколько агентов реально спавнится).
  Значения по умолчанию минимальные.
- **Объяви активный набор**: `/team-release` называет десять агентов и запускает одного. Перед первой
  фазой скилл обязан напечатать, кто будет запущен, а кто упомянут, но не запущен, иначе читатель не
  отличит корректно свёрнутый прогон от сломанного.
- **`/start` и `/project-stage-detect`**: онбординг читает проект скриптом, спрашивает, где пользователь
  находится, выводит rigor из его слов и записывает в `project.yaml` после явного «да».
- **Файл-чекпоинт `production/session-state/active.md`** с регионом CHECKPOINT, который перезаписывается
  и читается хуком на старте. Та же идея, что наш SESSION.md.
- **Правило для скриптов**: «хелперы выдают наблюдения, а не вердикты». Скрипт, который судит, рано или
  поздно противоречит режиму, которого не видит.
- **Собственное измерение автора**: четыре игры по одному брифу; на rigor `standard` до первой строки
  кода написано 30 документов за 58 минут, и слепые ревьюеры поставили эту сборку последней. 29 лишних
  документов купили трассируемость, а не игру. Автор сам подтверждает тезис статьи Anthropic.

Минусы. 49 агентов и 74 скилла это тот самый sprawl из статьи; один `effects-map.md` настолько велик,
что документация запрещает читать его во время прогона. Протокол «спроси "можно записать в путь" перед
каждым Write» делает каждую задачу медленной. Зависимости от Python и bash для хуков. Всё заточено под
игровую студию, переносятся формы, а не содержание.

## Вопрос 1: правильно ли декомпозированы агенты

### Карта по критериям статьи

| Агент | Почему сабагент | Критерий статьи | Вердикт |
|---|---|---|---|
| php-reviewer, python-reviewer, js-reviewer | читает код свежим взглядом, выход компактен | свежий контекст, проверка чёрного ящика | оставить |
| contract-reviewer | уходит в код вызываемой стороны, иногда в другой репозиторий | независимый путь исследования | оставить |
| review-verifier | состязательная проверка чужих находок | проверка чёрного ящика | оставить |
| design-reviewer | «приходит без истории обсуждения» и в этом его смысл | свежий контекст как требование | оставить |
| architect, backlog-planner, qa-expert | сканируют весь репозиторий, пишут один файл в фиксированный путь | раздувание контекста | оставить |
| data-analyst | профилирует датасет, пишет один HTML | раздувание контекста | оставить |
| devops-engineer, test-automator | меняют инфраструктуру и тесты, ограниченный набор инструментов | ограничение инструментов | оставить |
| php-developer, python-developer | пишут код по задаче | ни один из трёх напрямую | оставить с контрактом входа |
| analyst-writer | Analyze это диалог; Draft и Explain часто идут веером по N задачам | веер: параллельно, свежий контекст, выбросить | знание в скилл, тонкий агент для веера |
| facilitator | план встречи строится в диалоге, 293 строки знания | должен говорить с пользователем | перевести в скилл, знание уже в facilitation-patterns |

### Билдеры: слабое место, но не ошибка

Билдер как сабагент теряет всё, что обсуждалось до него: ограничения, отвергнутые варианты, стиль
проекта из беседы. Ему достаётся только текст промпта вызова. В интерактивной сессии это хуже, чем
главный цикл со скиллом `python-patterns`: главный цикл видел всё. Так что для работы «я сижу и правлю
вместе с Claude» билдер-сабагент избыточен, и статья права.

Билдер оправдан в двух случаях. Первый: оркестрация, где вход самодостаточен (тикет плюс расширенные
требования, как `patch` у openronin). Второй: экономия, билдеры у нас на sonnet, остальные на opus.
Оба случая требуют одного: у билдера должен быть явный контракт входа, иначе качество зависит от
того, насколько полно главный цикл пересказал контекст. Сейчас в `php-developer.md` и
`python-developer.md` секции «Input» нет, есть только «Workflow» и «When Reporting Done». Карта
перекрёстных ссылок показывает ту же дыру: на билдеров не ссылается ни один агент, их выход никто не
ожидает в определённой форме, хотя ревьюеры после них стоят в цепочке по README.

### Разговорные агенты: знание в скилл, агент только там, где есть веер

Analyst-writer и facilitator нарушают правило статьи «передавай беседу, только если сабагент должен
говорить с пользователем», с поправкой на Claude Code: сабагент здесь говорить с пользователем не может
вообще. Analyst-writer в режиме Analyze обязан сформировать уточняющие вопросы и, по README, создаёт
задачи в трекере «только после одобрения пользователем». Как сабагент он возвращает вопросы результатом,
главный цикл показывает их, пользователь отвечает, и следующий вызов снова начинается с нуля. Каждый круг
это потеря деталей.

Для facilitator дублирование уже есть: `facilitation-patterns` содержит ту же модель (пирамида целей,
главный вопрос, каталог методов). Агент добавляет процесс сборки плана и фиксированный скелет. Оба
переносятся в SKILL.md без потерь, а главный цикл сохраняет диалог. План встречи почти всегда строится
в диалоге, веера по N встречам в практике нет, поэтому агентский файл здесь не нужен.

У analyst-writer есть кейс, который скилл не закрывает: нужно завести N задач, и основной поток
запускает N аналитиков, каждый пишет описание своей. Это второй критерий статьи (параллельно, свежий
контекст, после задачи выбросить), и для него агент нужен. Решение гибридное. Знание (три режима,
разделение фактов и допущений, проверка соразмерности, скелеты вывода) переезжает в SKILL.md с роутингом
на `explanation-patterns` и `ru-output-style`, которые агент и так загружает по Glob. Агентский файл
сокращается до тонкой обёртки: описание для авто-роутинга, инструменты, модель, инструкция «загрузи
скилл, выполни названный режим, верни результат в этом формате». Оба пути вызова читают одно знание,
сейчас 278 строк агента это роль и знание в одном файле.

Разделение труда в веере:
- общую часть основной поток делает один раз inline со скиллом: уточняет задачу целиком с пользователем,
  режет на N, фиксирует общий словарь, формат описания и критерий готовности. Это та часть, где нужны
  вопросы, и её нельзя раздавать N агентам, иначе каждый задаст свои;
- N сабагентов получают одинаковый по форме бриф (своя задача, общий словарь, формат, что уже решено) и
  возвращают черновик или `NEEDS_INPUT` с вопросами и тем, к какому результату ведёт каждый ответ;
- основной поток собирает черновики, проверяет их между собой (одни термины, нет дублей), показывает
  пользователю и после одобрения заводит задачи в трекер сам. Создание в трекере N агентам не отдавать,
  правило «только после одобрения» в веере иначе не удержать.

Правило выбора для основного потока: материал самодостаточен и выход это документ, делегировать;
материал это беседа или нужна итерация с пользователем, загрузить скилл и работать самому. Второй круг
`NEEDS_INPUT` от одного и того же сабагента это сигнал, что режим Analyze надо было вести inline.

### Что уже сделано правильно и чего нет

Прогрессивное раскрытие реализовано образцово: SKILL.md тонкий, `references/*.md` по роутингу, агент
читает только нужный раздел. Фиксированные скелеты выходов (матрица QA с устойчивыми id, бэклог с ICE)
дают сравнимость между проектами. Ревью-семейство собрано в цепочку в README: языковой ревьюер, затем
contract-reviewer, затем review-verifier перед публикацией автору.

Чего нет:
- **Контракты между звеньями.** Единственная запись пайплайна это абзацы прозы в README. Game Studios
  держит для этого CONTRACT.md, openronin строгий JSON. У нас цепочка «qa-expert отдаёт e2e-пробелы
  test-automator» живёт через путь файла `docs/qa/COVERAGE-MATRIX.md`, и это работает; для билдеров и
  ревьюеров аналогичного файла нет.
- **Конфиг на уровне проекта.** Какие агенты активны в этом репозитории, какие стадии обязательны,
  когда спрашивать. Без этого каждая сессия заново угадывает, и приходится подсказывать руками.
- **Терминальные состояния.** Агент, который не смог (нет доступа к коду вызываемой стороны, ADR в статусе
  Proposed, тест-раннер не настроен), сообщает это прозой, а не именованным состоянием, которое главный
  цикл обязан показать.
- **Eval на маршрутизацию.** Статья просит отслеживать, выбран ли нужный сабагент. У нас eval есть только
  у `ru-output-style`.

## Вопрос 2: концепт пайплайна

### Универсального пайплайна нет, универсальный скелет есть

Оба репозитория пришли к одной конструкции: фиксированный порядок стадий и конфиг, который стадии
включает. Полосы openronin: уточнить, реализовать, (проверить), ответить на замечания, слить. Путь
Game Studios: дизайн, истории, реализация, ревью, закрытие, с рычагом rigor, который решает, какие
стадии обязательны. Содержание стадий совпадает с нашей цепочкой из README, если её дописать:

| Стадия | Кто | Вход | Выход | Когда обязательна |
|---|---|---|---|---|
| Уточнение | главный цикл, скилл analyst | тикет, беседа | расширенные требования, список вопросов | всегда; при вопросах стоп |
| Проектирование | architect | требования, код | ADR или короткий ответ | одностороннние двери: схема данных, граница сервиса, публичный API |
| Критика дизайна | design-reviewer | ADR или диф | сценарии-опровержения | те же одностороннние двери |
| Тест-стратегия | qa-expert режим 1 | требования | TEST-STRATEGY, матрица | новая фича с несколькими уровнями тестов |
| Реализация | билдер по стеку или главный цикл со скиллом | требования, ADR, матрица | диф, отчёт «что запущено» | всегда |
| Ревью кода | языковой ревьюер | диф | находки с severity | всегда |
| Ревью контрактов | contract-reviewer | диф | четыре гейта на вызов | диф пересекает границу модуля |
| Верификация находок | review-verifier | находки | CONFIRMED, REFUTED, UNPROVEN | находки уходят автору или в PR |
| Покрытие | qa-expert режим 2, test-automator | диф, матрица | обновлённая матрица, e2e | standard и выше |
| Доставка | devops-engineer, главный цикл | зелёный диф | PR, релиз | по проекту |

Что меняется от проекта к проекту: стек (какой билдер и ревьюер), какие стадии обязательны (rigor),
пути артефактов, где живёт трекер, язык вывода, зоны «не трогать», definition of done. Это ровно поля
чартера openronin плюс rigor из Game Studios. Таблица выше универсальна; заполненная для проекта копия нет.

### Нужен скилл, который заполняет скелет на старте

Это должен быть скилл, а не агент, по той же причине, что и analyst-writer: он задаёт вопросы
(размер задачи, обратимость, кто ревьюит, сколько автономии), читает репозиторий и пишет файл после
явного согласия. Сабагент не может ни спросить, ни дождаться ответа. Game Studios делает это скиллами
`/start` и `/project-stage-detect`, и это у них одна из самых аккуратных частей.

Рабочее имя: `pipeline-init` (скилл) с опциональным `pipeline-check` (проверка, что стадии прошли).
Фазы:

1. **Прочитать проект скриптом.** Манифесты и локфайлы (стек), CI-конфиг, тест-раннеры, наличие
   `docs/adr`, `docs/qa`, `docs/backlog`, CLAUDE.md, `.claude/agents` в проекте. Скрипт выдаёт
   наблюдения, а не вердикт (правило Game Studios), решение принимает модель в диалоге.
2. **Спросить три-четыре вещи.** Тип работы (баг, фича, новый сервис, рефакторинг, исследование);
   обратимость изменений (есть ли схема данных, публичный API, граница сервиса); режим автономии
   (спрашивать на каждом переходе, только на крупных, не спрашивать); кто читает результат (ревьюер-человек,
   PR, трекер).
3. **Показать карту, потом записать.** Как `/start`: карточка «что я настрою», явное «да», запись.
   Обязательно напечатать активный набор и то, что названо, но не запущено.
4. **Записать на двух уровнях**, по тому же принципу, что ваш протокол памяти. Тонкий блок в
   `<repo>/CLAUDE.md` (пять-восемь строк: стек, активные агенты, обязательные стадии, где конфиг)
   и толстый `docs/PIPELINE.md` (или `.claude/pipeline.yaml`) с таблицей стадий, путями артефактов,
   definition of done, зонами «не трогать», состояниями-тупиками. Тонкий блок загружается в каждую сессию
   и отвечает на вопрос «какие и где агенты нужны» без подсказки руками.

Файл пайплайна стоит делать по типам задач, а не один на проект: строка «багфикс: architect пропустить,
contract-reviewer только если диф трогает клиент внешнего сервиса» и строка «фича с миграцией: architect,
design-reviewer, qa-expert режим 1 обязательны». Тогда скилл запускается один раз на проект и
перечитывается на старте задачи, а не переписывается.

### Где взять enforcement, если harness'а нет

Без принуждения пайплайн это совет. У openronin его исполняет код роутера, у Game Studios хуки
(`validate-write.sh`, `pre-push-test-gate`) и скилл `/gate-check`. Для claude-dev-agents лестница такая:

- **Уровень 0, совет.** Блок в CLAUDE.md с MUST: «перед PR прогнать python-reviewer и review-verifier».
  Работает в той мере, в какой модель читает CLAUDE.md, то есть обычно работает.
- **Уровень 1, чек-лист.** Скилл `pipeline-check` перед доставкой читает `docs/PIPELINE.md`, ищет
  артефакты стадий (файл матрицы обновлён, в беседе есть вердикт ревьюера) и печатает «пройдено, пропущено,
  пропущено с объяснением». Как `/gate-check`, но без 150 строк.
- **Уровень 2, хук.** PreToolUse на `git push` или `gh pr create`, который проверяет наличие квитанции
  ревью (файл или маркер в коммите) и блокирует, если нет. Это уже механизм Game Studios
  (`review-receipts.sh`); вводить после того, как уровень 1 покажет, что стадии реально пропускаются.

Начинать с нулевого уровня и измерять, как советует статья: менять по одному и держать то, что
подтверждается. Собственный замер Game Studios (30 документов, последнее место) это предупреждение
против полного набора стадий по умолчанию.

### Лестница доверия вместо переключателя

Режим автономии стоит брать не бинарным, а как у openronin: `propose` (скилл предлагает стадии и
ждёт), `guided` (крупные переходы спрашивает, мелкие проходит), `autonomous` (идёт до конца, пишет
журнал решений). Начинать проект с `propose`, поднимать после нескольких задач без правок руками.

## Пробелы: чего в цепочке нет

Согласованный список (2026-10-29). Делится на пробелы в цепочке стадий, где у скелета нет
исполнителя, и на асимметрии внутри репозитория.

В цепочке:
- **Ответ на ревью со стороны автора.** Находки производятся, но никто их не потребляет в
  определённой форме. Скилл `address-review`: вход это список CONFIRMED находок, выход это статус по
  каждой (addressed, declined, clarifying) и диф. Скилл, а не агент: правки требуют контекста задачи.
- **Расследование причины сбоя.** Агент `root-cause-investigator`, read-only: гипотезы,
  воспроизведение, бисект. Проходит два критерия статьи (свежий контекст, параллельные гипотезы).
  Его выход становится входом analyst-writer для постмортема.
- **Карта существующего репозитория.** Закрыта скиллом `/onboard-memory` из
  claude-memory-3layer, см. раздел ниже; отдельный `codebase-map` не нужен.
- **Кросс-языковой security-ревьюер.** Auth-модель, секреты, SSRF, зависимости с уязвимостями, права
  в CI. Агент: чёрный ящик, компактный выход.

Асимметрии:
- Триада «билдер, ревьюер, скилл» есть только у PHP и Python. js-reviewer без скилла (310 строк, знание
  внутри), devops-engineer без скилла (95 строк). Скиллы `js-patterns` и `devops-patterns`.
- Миграция проходит ревью только как часть дифа, без проверки блокировок, порядка выката и отката.
  См. SQL ниже.
- Линт агентов (BL-011 в бэклоге открыт): обязательные секции, совпадение `name` с файлом, в CI.

Низкий приоритет: release-notes, docs-writer, скилл ретро для захвата gotchas.

### По каждому пробелу

**SQL и миграции.** У ECC `database-reviewer` (100 строк, Postgres и Supabase: RLS, `auth.uid()`) с
хорошим списком антипаттернов (int в id, timestamp без зоны, OFFSET-пагинация, FK без индекса, порядок
блокировок, SKIP LOCKED для очередей) и скилл `database-migrations` (430 строк: expand-contract,
конкурентные индексы, бэкфилл батчами, workflow для Prisma, Drizzle, Kysely, Django, golang-migrate). У
VoltAgent `sql-pro` это широкий чек-лист (оконные функции, уровни изоляции, хранилища), без правила
доказательств. Вывод: мой пункт «чек-лист миграций в design-reviewer» слишком мал. Нужен скилл
`sql-patterns` с references по схеме и индексам, по безопасности миграций и по нашим ORM (Doctrine,
Eloquent, Django ORM, SQLAlchemy с Alembic), который читают php- и python-ревьюеры и билдеры. Отдельный
агент `db-reviewer` по критериям статьи оправдан (чёрный ящик над дифом, как contract-reviewer), но
заводить его стоит после скилла и только если ревью миграций случается регулярно. Источник для references:
ECC `database-migrations` и список антипаттернов `database-reviewer`, с заменой JS-инструментов на наши.

**Security.** ECC `security-reviewer` (117 строк) делегирует в скилл `security-review` (511 строк) и
держит таблицу «паттерн, severity, лечение» и раздел «частые ложные срабатывания» (`.env.example`,
тестовые креды, SHA256 для контрольных сумм). Оба под Node: `npm audit`, `process.env`, раздел про
Solana. VoltAgent `security-auditor` это аудит соответствия (SOC 2, ISO 27001), не ревью кода;
`penetration-tester` вне нашей задачи. Вывод: предложенный `security-reviewer` делать своим,
языково-нейтральным, с командами по стекам в references (`composer audit`, `pip-audit`, `npm audit`),
с выходом в формате наших ревьюеров, чтобы находки шли в review-verifier. Из ECC взять таблицу
паттернов, раздел ложных срабатываний и список триггеров (auth, пользовательский ввод, запросы к БД,
пути файловой системы, внешние вызовы, криптография, секреты). Этот же список триггеров становится
правилом пайплайна, когда security-стадия обязательна.

**Расследование сбоев.** VoltAgent `debugger` и `error-detective` это чек-листы с правами на запись,
они и ищут, и чинят. ECC делит иначе: `build-error-resolver` (узкая роль: только ошибки сборки и
типов, минимальный диф, никакой архитектуры) и `silent-failure-hunter` (59 строк: пустые catch,
опасные дефолты, потерянные стеки). В `orch-fix-defect` первый ход это воспроизвести баг падающим
тестом, потом чинить. Вывод: `root-cause-investigator` оставить read-only, а артефактом передачи
билдеру сделать падающий тест плюс гипотезу. Silent-failure-hunter заводить не как агента, а как
раздел чек-листа в языковых ревьюерах.

**Ответ на ревью.** Ни в одном наборе прямого аналога нет. ECC в `orch-pipeline` только требует
«CRITICAL и HIGH закрыты до гейта коммита». Ближайшая форма у VoltAgent `docs-drift-editor`: верхний
агент решает, что менять, нижний делает минимальные правки, возвращает JSON с `edited` и `skipped` и
причинами, и имеет ограничитель радиуса (правка больше 40% файла превращается в маркер TODO и
пропуск). Эта форма переносится в `address-review` целиком: статус по каждой находке, причина
отказа, ограничитель на правки вне дифа.

**JS и Vue.** ECC `vue-patterns` (471 строк: структура, композаблы, Pinia, роутер, Nuxt, API Vue 3.5,
антипаттерны) и `vue-reviewer` (206). VoltAgent `vue-expert` и `typescript-pro` шаблонные. Вывод:
`js-patterns/references/vue.md` дистиллировать из ECC `vue-patterns`; наш js-reviewer (XSS,
реактивность, утечки слушателей) с ним не пересекается, а дополняет.

**DevOps.** У ECC есть `docker-patterns`, `deployment-patterns`, `kubernetes-patterns`, `github-ops`;
не читал глубоко, но как сырьё для `devops-patterns` они подходят по форме.

### Пересечения с пайплайном

ECC `orch-pipeline` это ближайший аналог pipeline-init, но другого уровня: не конфиг проекта, а
классификатор на каждый запрос. Пять операций (add-feature, change-feature, fix-defect, refine-code,
build-mvp), четыре размера (trivial, small, standard, large) по трём сигналам (сколько файлов, новая
зависимость или контракт, неясность дизайна), и маска фаз на каждую пару. Два гейта: после плана и
перед коммитом, между ними без остановок. Что взять: строки файла пайплайна строить по операции и
размеру, где тип задачи это одна из осей; два гейта как минимальный набор точек решения; правило «security
обязателен, если диф трогает триггер» как образец правила включения стадии.

ECC `change-impact`: до изменения радиус (код, данные, интерфейсы, тесты, документация, релиз), после
изменения сверка «диф не вышел за заявленный scope». Первая половина пересекается с design-reviewer и
contract-reviewer, вторая это готовый пункт для `pipeline-check`. ECC `verification-loop` (сборка,
типы, линт, тесты с покрытием, grep секретов, обзор дифа, отчёт PASS/FAIL) это уровень 1 лестницы
принуждения с конкретными командами, под JS. ECC `delivery-gate` это Stop-хук, уровень 2; проверяет он
гигиену журнала обучения, что нам не нужно, но механика (детерминированные проверки, блокировка не
чаще одного раза за Stop) переносится.

Попутные находки. VoltAgent `surgeon-reviewer`: severity по последствию (WILL BREAK, WILL COST, WILL
ROT), «опровергни до публикации», вердикт SHIP или DO NOT SHIP; пересекается с review-verifier, но
имена ярусов по последствию лучше наших CRITICAL, HIGH, MEDIUM, стоит обсудить. VoltAgent
`ai-writing-auditor`: английский аналог ru-output-style (34 категории, словарь из 103 слов по трём
ярусам), источник на случай en-output-style. ECC `council` (скептик, прагматик, критик для go/no-go)
дублирует design-reviewer. ECC `pr-test-analyzer` слабее qa-expert в режиме 2.

## Карта репозитория: /onboard-memory закрывает запрос

Скилл `/onboard-memory` из [claude-memory-3layer](https://github.com/lastangel001/claude-memory-3layer)
(197 строк плюс `bin/onboard-report.sh` на 215) делает то, что я назвал `codebase-map`, и больше:
скрипт собирает стек, документацию, структуру, точки входа, outline символов через ctags, конфиги,
историю, горячие файлы, FIXME и deprecated; скилл пишет `CLAUDE.md` до 60 строк и `.claude-docs/`
с architecture.md (слои, порядок чтения, бизнес-потоки), conventions.md, gotchas.md и index.md, с
режимом UPDATE по дельте коммитов и запретом выдумывать. Это та же пара «тонкий вход, толстые
справочники», что нужна pipeline-init.

Чего в отчёте нет для пайплайна: содержимого CI (какие джобы и гейты есть, что блокирует merge),
CODEOWNERS и шаблона PR, каталога миграций, клиентов внешних сервисов и очередей (то, что делает
contract-reviewer обязательным), топологии тестов по уровням. Конфиги тест-раннеров скрипт ловит
(`phpunit.xml`, `pytest.ini`), остальное нет.

Решение: `codebase-map` из списка убрать. pipeline-init читает `.claude-docs/architecture.md`, если
он есть, и дополняет коротким сканом «сигналов пайплайна» (CI, CODEOWNERS, миграции, внешние вызовы,
тесты по уровням). Зависимость мягкая: без `.claude-docs/` скилл делает свой лёгкий скан и советует
прогнать `/onboard-memory` первым. Оба репозитория публичные под одним владельцем, так что ссылка
между ними допустима; жёсткой зависимости в установщике не делать.

## Что делать в репозитории, по убыванию отдачи

1. **Секция «Input» и «Handoff» у билдеров и ревьюеров.** Формат CONTRACT.md Game Studios, сокращённый
   до четырёх полей: что обязано быть на входе, что гарантируется на выходе, что ожидает следующее звено,
   где ломается. Дешевле всего, закрывает дыру «на билдеров никто не ссылается». Минорный релиз.
2. **Скилл `pipeline-init`** с скриптом-наблюдателем и шаблоном `docs/PIPELINE.md`. Это ответ на второй
   вопрос; без него каждый проект стартует с устных подсказок.
3. **Именованные состояния-тупики** в каждом агенте: `NEEDS_INPUT` (вопросы вместо результата),
   `BLOCKED` (нет доступа, нет инструмента), `OUT_OF_SCOPE` (просили не то). Главный цикл обязан их
   показать, а не пересказать. У design-reviewer и review-verifier это уже почти есть через «Open questions».
4. **Facilitator в скилл, analyst-writer в скилл плюс тонкую обёртку.** Агент facilitator удалить при
   следующем мажоре. Агент analyst-writer сократить до обёртки для веера, а бриф веера (своя задача,
   общий словарь, формат, что решено) записать как его контракт входа.
5. **Eval маршрутизации**: десять золотых запросов, для каждого ожидаемый агент или скилл. Статья
   считает десять примеров достаточным стартом. Запускать сабагентами из сессии, как уже делается для
   `ru-output-style`.

Новые скиллы и агенты из раздела «Пробелы», в порядке после пунктов 1-5:

6. **Скилл `address-review`** по форме docs-drift-editor: статус по каждой находке, причина отказа,
   ограничитель на правки вне дифа. Замыкает цепочку ревью.
7. **Скилл `js-patterns`**, references по Vue дистиллировать из ECC `vue-patterns`. Самая дешёвая
   асимметрия; js-reviewer после этого худеет.
8. **Агент `root-cause-investigator`**, read-only, артефакт передачи это падающий тест плюс гипотеза.
   Единственный новый агент, который проходит критерии статьи без оговорок.
9. **Скилл `sql-patterns`** (схема и индексы, безопасность миграций, наши ORM), источники ECC
   `database-migrations` и антипаттерны `database-reviewer`. Агент `db-reviewer` только после скилла и по
   фактической частоте ревью миграций.
10. **Агент `security-reviewer`**, языково-нейтральный, выход в формате ревьюеров для review-verifier;
